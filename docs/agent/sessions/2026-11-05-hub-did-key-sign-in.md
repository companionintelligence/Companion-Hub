# Sign in with a DID (flag-gated)

> **This change touches sign-in. It needs the Hub security reviewer before merge,** and it ships off: nothing is reachable until `CI_HUB_DID_AUTH=true` is set.
>
> The first commit built the feature. Three more fix what an independent adversarial review found, one round each: 21 confirmed findings and 2 contested ones in the first ("Second review"), then what the next rounds found in the fixes ("Third review", "Fourth review"). A merge of `origin/dev` (PR #2247) sits between the third and fourth ("Merge of origin/dev"). Where the rounds disagree, this page describes the latest.

## Goal

Add an optional way to sign in with a DID, off by default, without creating a person or a binding from a DID alone, without resolving any DID, without touching forward auth, and without importing or unfreezing the frozen KERI module.

## Decisions

| Decision | Rationale |
| --- | --- |
| Store a link as a `federated_identity` row, issuer `did:key`, subject the full `did:key:z6Mk…`; no migration | The table is the Hub's existing (issuer, subject) to person binding and already has the unique index. A second table would be a migration for one more `(issuer, subject)` pair. |
| `linksForCurrentPortal` drops every `did:` issuer | Shared table, Portal-assuming readers. Without it a person whose only link is a DID gets asked about at Portal, answered "not a member", and revoked (`reconcileOperatorMemberships`, the session refresh, and `MarketplaceWhoIsService.portalSubject`). A Portal link is never dropped: its issuer is a URL. |
| The proof is a SIOPv2-shaped self-issued ID token | The contract does not depend on a transport. SIOPv2's request-object transport can be added later without changing what the Hub verifies. Whether any Local.Pub client or wallet will sign a Hub challenge is unknown and untested. |
| The audience is `urn:ci-hub:<directory id>` (the issuer forward auth already signs under), not an origin | A Hub is reached under several names (`*.ci.localhost`, a tailnet name, a tunnel); its directory id is the one name it always has. A proof for another Hub or for Portal does not verify. The cost: the anonymous challenge route shows that id (see Open items). |
| The key comes from the DID only; `jwk`, `jku`, `x5u` and `kid` select nothing | Otherwise the token chooses its own verifier. `kid` is allowed only as the DID or `<did>#…`. |
| **Weak Ed25519 keys are not DIDs** (second commit) | A small-order point (order 1, 2, 4 or 8) makes a signature verify for any message with no private key, so a DID for one is a factor nobody has to hold. A `y` of at least 2^255 − 19 is a second spelling of a point, so one key would have two DIDs. `isWeakEd25519Key` refuses all 14 small-order encodings and every such `y` with BigInt arithmetic and no curve library. The five `y` values were produced in Python (RFC 8032 group law) and are re-derived in `did-key.test.ts`. The first commit called these keys "canonical" and listed two of them as valid test vectors. (Third commit, reworded in the fourth:) a string of 32 bytes that is not a point on the curve is refused too (`isEd25519CurvePoint`, RFC 8032 section 5.1.3), as defence in depth. Nothing verifies under such a key and no Hub route links a DID that was typed in, so it changes no Hub outcome. It is **not a typo guard**: one wrong character in a `did:key` is another valid `did:key` about 46% of the time (measured here with `isDidKey` on 21,432 single-character substitutions of 8 random keys: 46.2%; the review measured 45.8% and 46.0%). (The third commit said the opposite, which was copied from Companion Memory, where an owner does type a peer's DID.) The function is a port of Memory's. Its 130 distinct vectors, produced by an independent Python implementation of the RFC's own decoding, are in the fixture; Memory's spec carries a subset of them. The byte-level helpers are now total: anything that is not exactly 32 bytes in a `Uint8Array` is weak, not a point, and has no DID. |
| **A challenge has one purpose, `sign-in` or `link`, and that does not stop a relayer** (second commit, corrected in the third) | The purpose is set when the challenge is issued (`POST /did/challenge {purpose}`, default `sign-in`), and a proof presented for the other purpose is refused and the challenge spent. That stops a Hub page mixing the two up, and it stops a *sign-in* challenge fetched by the victim being redeemed as a link. It does not stop a relayer: the purpose is chosen by whoever calls the public challenge route, which is the relayer, and it is not among the signed claims, so the signer's wallet never sees it. A relayer who asks for a `link` challenge, shows it as a login and redeems the signature on `/did/link` from their own session plants the signer's DID on the relayer's person (the signer's own link then fails with a 409, and their DID signs in as the relayer's person). The second commit's wording said the opposite. The real fix, a signed purpose or request object plus a way for a key's holder to release a link, is not in this change (TODO). |
| `exp` must be later than `iat` (second commit) | A token that expired before it was issued was accepted inside the clock tolerance. |
| The challenge is deleted on first read, valid proof or not | A failed guess costs a fresh challenge, and a captured proof cannot be tried twice. |
| On `/did/verify`, one 401 body for every verification failure and for a revoked or deleted person; a 403 `AUTH_ERROR_DID_NOT_LINKED` only after the signature verified | The caller learns nothing about which check failed. The 403 is reached only by someone who proved control of the key. |
| **On `/did/link`, a proof that does not verify is a 400, not a 401** (second commit) | The SPA reads any 401 outside `SESSION_EXPIRY_EXEMPT_PATHS` as "your session ended" and signs the person out. `/did/link` is used while signed in, so a wallet that signed wrongly must not end the session. `/api/auth/did/verify` is anonymous and 401 is its answer, so it is on the exempt list. |
| **Every refusal is a `TranslatableError` with an i18n key** (second commit) | The first commit documented and tested `code` fields (`DID_NOT_LINKED` and the rest) that `MainExceptionFilter` drops from a plain `HttpException`: no client ever received one. Every other auth route answers `{statusCode, message, path}` with the key in `message`; these do too, with eight new keys in `en.json` and `en-US.json`. Chosen over changing the filter, which every route shares. |
| **A person with TOTP on still gives the code** (`/did/verify` answers `totpSessionId`) | A deviation from "like Portal SSO". The Portal sign-in routes (`/auth/portal/callback`, and the mobile and desktop session routes, the last added by #2247) create their sessions without asking for the Hub's TOTP, and no source records why. A person who turned TOTP on chose a second factor. Cheap, reuses `/auth/verify-totp`, and easy to relax if the reviewer disagrees. (The first commit said "because Portal is the authority there"; that rationale was the author's inference and is gone.) |
| **`/did/verify` makes the session-refresh membership check** (second commit) | The first commit tested only the local `accessStatus`, so a person Portal had just removed could sign in with a linked DID until the next sweep. `AuthService.assertStillOrgMember` (extracted from `refreshSession`) asks Portal for a person with a Portal link, by that subject: "not a member" revokes and answers 403; a member is marked active. That includes a person whose only Portal link is from another Portal, who is asked about it and revoked on a definitive "not a member", as the sweep and the refresh have always done (#2178). **When Portal cannot be reached, answers with an error, or is not configured, the person is let in.** A person with no Portal link at all is not asked. It still does not go through `admitHubPerson`. (Third commit:) the method no longer reads the registration itself before asking; `resolvePairedOrgMembershipDetail` does, and answers "unknown" when the read fails and `unpaired` when there is none, and an `unpaired` answer never revokes, exactly as in `applyOnlineMembership`. The first version's unguarded read answered 500 where the password path lets the person in, and a registration reset racing a sign-in could revoke the person. The session refresh shares the method, so it gains the same two rules. |
| Link, unlink and list need `hubPrincipal === 'session'`. Link and unlink are also refused when the browser says another site sent them, when `Origin` names another host or port than the request's own, and unless the body is JSON (second commit) | The Portal push key, the host-local key and the CLI token all speak as the first operator. `Sec-Fetch-Site` alone does not cover a Hub reached over plain http at a LAN name (a browser sends it only to https and loopback URLs), and a form post is a CORS "simple" request that carries the cookie without a preflight. `Origin` is on every cross-origin POST and DELETE; requiring JSON forces the preflight, which the Hub answers for its own origins only. A request with none of those headers (`curl`, the CLI) passes. The desktop shell's origin is refused until a screen exists. |
| 404 from `DidAuthFlagGuard`, which runs before `AuthGuard`, and it is the 404 Nest gives an unknown path (second commit) | With the flag off the surface is absent for signed-in and anonymous callers alike. The first commit's 404 had its own message and a different `path`, so the two were distinguishable. A test boots a second app without the routes and compares status, body and headers for 44 request shapes as each of four callers (anonymous, a signed-in person, the host-local key, the Portal push key), including GET, HEAD, POST, PUT, PATCH, DELETE and OPTIONS and absolute-form targets (the third commit's fix: Express keeps the scheme and host of an absolute-form target when it strips a mount, so the first fix still told the two apart for `GET http://host/api/… HTTP/1.1`; the fourth's: the path is built from `request.url`, which Express has already normalised, because a backslash in an absolute-form target is a slash to its router). **The claim is narrower than "cannot be told from a build without the feature":** it holds for origin-form requests and for the absolute-form forms the twin test covers, not for the production image's SPA fallback or for `/api/docs-json` (see Open items). The twin test boots neither. `AuthController` takes the service as its last, `@Optional()` parameter, so existing tests that build the controller without it keep passing. |
| **Link and unlink are refused in demo mode** (third commit) | `DemoModeGuard`, after `HubSessionGuard` so the flag-off answer is unchanged. Demo mode already stops the shared user changing the password, the username and TOTP; a DID link is a way in that none of those removes. The shared helper answers with the key `SERVER_ERROR_NOT_ALLOWED_IN_DEMO` and the default status of a `TranslatableError`, which is 500, as on every route that uses it; the review expected 403. Changing the status would change those routes too, so it is not done here. |
| The DID DTOs are in `SWAGGER_ZOD_DTOS` (second commit) | Unlisted, they generated as empty objects in `swagger.json` and the client, and the drift gate passed because it compares the generator with itself. The generated schemas now carry their properties. |
| Reuse `AuthController`'s private cookie helpers by putting the routes in that file | The Domain and Secure rules for the session cookie are security-sensitive; a copy would drift. The block is delimited (`// ── Sign in with a DID ──`). |
| Did not regenerate `docs/agent/TEST_INVENTORY.md` | As in `hub-keri-freeze`, it is stale at the base and regenerating would pull unrelated rows into this change. |

## Open items / handoff

- **Needs the Hub security reviewer before merge** (the change adds a way to obtain a session).
- **Not verified, and not claimed:** no Local.Pub client or wallet has been checked against the token, and none is known to sign one; the Hub was not run end to end; Traefik and Postgres were not in the loop; CI is manual-dispatch, so nothing ran there. The HTTP test runs the real Nest stack with the users, links, cache and Portal faked.
- **Open item: a step-up to link.** Changing the password asks for the current password; linking a DID asks for nothing but a session. A stolen session can link the thief's DID and keep a way in after it ends. Recommended: require the password (or TOTP) to link. A person who only ever signs in through Portal has no local password to ask for, which is why it is not in this change.
- **Open item: what a link outlives.** Changing the password or the username, the operator password reset and a Portal removal all end sessions and leave every DID link, and the operator reset also turns TOTP off, after which `/did/verify` for a linked DID opens a session with no second factor. Nothing but the generated client calls these routes, so no screen or command lists or removes a link (TODO `did-sign-in-link-surface`). Decide whether a password change or an operator reset should list or drop links.
- **Known residual: a scanner can still tell a Hub with the flag off from a build without the feature.** In an image with the frontend bundle, the SPA fallback answers an absolute-form `GET` or `HEAD` for `/api/…` with `index.html` on a build without the routes, where this Hub answers 404; outside `NODE_ENV=production`, `/api/docs-json` lists the five routes whatever the flag says. Origin-form requests, POST and DELETE are identical. The fix is to register the handlers only when the flag is set at startup, which a running process's environment cannot change; decided against for now (TODO `did-sign-in-absent-surface`).
- **Open item: relay, and the purpose does not stop it.** A person who signs this Hub's challenge on a page an attacker controls hands over a usable proof for up to 120 s, once. The challenge route is public, so the attacker needs nothing from the person's Hub to get a genuine challenge. The audience is an opaque per-install id that a wallet cannot map to a site, and in a relay it is the real Hub's, so showing it is no mitigation: nothing in the current token lets a person tell a relay from the real page. A signed SIOPv2 request object lets a wallet verify and show the Hub's name; it does not stop relay. A challenge has a purpose, and a proof for the other purpose is refused, but the purpose is chosen by the requester and is not signed. A relayer who asks for a `link` challenge, shows it as a login and redeems the signature on `/did/link` from their own session plants the signer's DID on the relayer's person: the signer's own link then fails with a 409, they cannot remove a row that is not theirs, and their DID signs in as the relayer's person. TODO: `did-sign-in-signed-purpose` (a signed purpose or request object) and `did-sign-in-release-link` (a way for a key's holder to release a link someone else made). Neither is in this change, by decision.
- **Disclosure: the challenge route is anonymous** and returns the Hub's directory id as `audience`: a per-install identifier that lasts until a factory reset. Forward auth gives that value (`X-CI-Hub-User-Issuer`) only to apps that hold a forward-auth key (Companion Memory, and any app whose env sets its own `CI_HUB_FORWARD_AUTH_SECRET`); an app without a key gets the username alone. So this is a new disclosure to anyone who can reach the Hub, for the reviewer to accept, or to replace with an audience that does not carry the directory id. (The second commit said apps already see it, third-party apps included; that was wrong.) The first call can also insert the `user_directory` row after a restore or a reset.
- **Open item: unlinking ends no session, and a lost or stolen key.** `DELETE /did/link` removes the row and nothing else. A session a DID opened is an ordinary seven-day session that slides, with no record of how it was made, so an owner who unlinks a lost or stolen key leaves any session it already opened alive until the password or the username is changed. With no screen or command that lists links, the owner cannot see which keys are linked. Decide whether an unlink should end the person's other sessions (TODO `did-sign-in-link-surface`).
- **Operator interface: the flag is read from the process environment, on every request.** A running Hub's environment does not change, so switching the feature off takes a restart or a recreated container. The second commit's docs said no restart was needed.
- **Demo mode answers 500, not 403.** The shared demo-mode helper throws `TranslatableError('SERVER_ERROR_NOT_ALLOWED_IN_DEMO')` with the default status of 500, on every route that uses it. The DID link and unlink routes inherit that. A 403 would be the right answer, and changing it changes those other routes, so it is a separate decision.
- **Deployment: the `Origin` check compares against the first `X-Forwarded-Host`, else `Host`.** A proxy that rewrites `Host` and sends no `X-Forwarded-Host` makes the Hub's own pages look cross-origin, and their link and unlink calls answer 403. Traefik sends it.
- Rate limits are keyed by client address like the other unauthenticated routes, so behind a proxy the Hub does not vouch for, every caller shares one budget (see `AuthRateLimiter`). Verify and link share one budget of 10 failures a minute.
- The Hub still emits no AID header, builds no `did:keri:` string and does not import the frozen module; `FROZEN.md` and `docs/security/hub-portal-trust.md` still say so truthfully.
- `docs/agent/TEST_INVENTORY.md` was not regenerated (stale at the base).
